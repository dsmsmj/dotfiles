# 用 Skill 把 AI 变成趁手的工具：我的 6 个 Cursor Skills 实践

## 一、开场：为什么要写 Skill（5 分钟）

我们每天都在跟 AI 说重复的话：

- "先别写代码，先给我一个计划……"
- "review 一下我暂存的改动，重点看 hooks 和类型……"
- "按 Conventional Commits 帮我生成 commit message……"

每次都要重新描述一遍规则、格式、注意事项。**Skill 就是把这些"重复的嘱咐"沉淀成文件**，让 AI 在对的时机自动加载对的工作方式。

一个 Skill 本质上就是一个 `SKILL.md`：

```
~/.cursor/skills/
└── my-skill/
    ├── SKILL.md      ← 核心：frontmatter(name + description) + 正文指令
    └── scripts/      ← 可选：外挂脚本，让 AI 调用
```

关键机制：**description 决定触发**。AI 根据用户说的话匹配 description 里的场景描述和触发词，命中就加载正文按协议执行。所以 description 不是"简介"，而是"路由规则"。

今天分享我在用的 6 个 skill，分两组讲：

1. **一条主线**：覆盖"一个需求从启动到提交"的完整生命周期（4 个 skill）
2. **两个独立能力**：修 bug 前先查产品文档、技术决策讨论（2 个 skill，各自解决各自的问题）

---

## 二、主线：一个需求的生命周期（15 分钟）

这四个 skill 正好对应日常开发的四个阶段，可以串成一条链演示：

```
需求启动                UI 实现细节            提交前              提交
legacy-feature-kickoff → iconfont → diff-git-review → quick-git-commit-no-verify
```

### 2.1 legacy-feature-kickoff — 老项目里怎么优雅地开新需求

**解决的痛点**：在存量项目里接新需求，AI 最容易犯的错是"上来就哐哐写代码"，无视现有的路由、状态管理、组件库，造出一套平行结构。

**这个 skill 做了什么**：

- 强制 **Plan first**——不经确认不写大段代码
- 要求先定位现有触点：页面、model/store、service、路由、权限
- 拿到 Figma 后先做"可复用组件 vs 新 UI"的映射，而不是照图新造
- 首次回复必须带一个开工清单（需求已总结 / 触点已定位 / Figma 映射已画 / 计划+风险已列 / 等待确认）

**分享点**：这是"流程型 skill"的典型——它不教 AI 新技能，而是**约束 AI 的行为顺序**。对老项目来说，"不乱来"比"能力强"更重要。

### 2.2 iconfont — 截图找 icon，写 UI 时的高频小事

**解决的痛点**：设计稿上一个 icon，在几百个 iconfont 图标里人肉翻 `font_class`，Figma 导出名还全是 `Frame`/`Vector` 这种无意义名字。

**这个 skill 做了什么**：

- 用户贴截图 + 手动 `@iconfont` 触发（设置了 `disable-model-invocation: true`，不让 AI 自作主张）
- 外挂两个脚本：`search.mjs` 按关键词搜 `iconfont.json`，`render.mjs` 把候选渲成 SVG
- 强制"视觉比对"步骤：AI 要真的看渲染出来的图和截图对比，不许只凭名字猜
- 输出统一格式：name / font_class / unicode / 组件库 `Icon` 的标准用法

**分享点**：两个设计技巧值得抄——

1. **skill + 脚本的组合**：SKILL.md 负责流程，脚本负责确定性计算，AI 负责模糊匹配（视觉比对）。各干各擅长的事。
2. **手动触发开关**：不是所有 skill 都该自动触发，高度场景化的工具用 `disable-model-invocation` 交给用户控制，避免误触发。

### 2.3 diff-git-review — 提交前的分层 Code Review

**解决的痛点**：让 AI review 代码，不给约束就会输出一大篇泛泛而谈；重点不突出，也不知道哪些必须改。

**这个 skill 做了什么**：

- 自动跑 `git diff --cached` 拿暂存区改动，不用手动粘贴
- 按 React/TS 项目定制了**三级分层检查表**：
  - 🔴 Blocking：Hook 违规、`any` 滥用、state 直接变异、敏感信息泄露……
  - 🟡 Optimization：组件超 150 行、Props Drilling、缺 Loading/Error 态……
  - 🟢 Style：魔法数字、命名歧义、a11y……
- 输出模板固定：`[文件:行号] 问题 —— 修复建议`，没问题的级别直接省略

**分享点**：**输出协议模板化**是让 review 结果可用的关键。同样的模型，有没有分级模板，结果的可读性天差地别。

### 2.4 quick-git-commit-no-verify — 免检快速提交

**解决的痛点**：改了个文案、调了个样式，也要等 pre-commit 跑完全量 lint；或者紧急修复时只想先提上去。

**这个 skill 做了什么**：

- 读 `git diff --cached`，按 Conventional Commits 自动总结出 commit message
- 强制带 `--no-verify`，并且**明确禁止**输出任何代码评价——它的定位就是"纯粹竞速"
- 输出极简：一条可以直接复制执行的命令，没有废话

**分享点 · 这两个 skill 是一对**：

`diff-git-review` 和 `quick-git-commit-no-verify` 是刻意设计的互补关系——一个严查、一个免检，并且它们之间有**自动衔接**：

- review 发现 🔴 Blocking 问题 → **拒绝**给提交命令，明确要求先修复
- review 通过 → 自动附上提交命令，并提示可加 `-n` 跳过 pre-commit

也就是说"跳过检查"不是无条件的：想快，可以，但 AI review 这一关先过。这比单纯 `git commit -n` 裸奔多了一层兜底。

## 三、两个独立能力（10 分钟）

下面两个 skill 和上面的主线没有流程关系，它们各自解决独立的问题。

### 3.1 product-docs-query — 修 bug 前先让 AI 读懂产品功能

**解决的痛点**：修 bug 时 AI 往往只盯着代码，不知道这个功能**本来应该怎么工作**——预期行为、边界条件、上下游联动，全靠猜。猜错了就会"修好了代码但改坏了产品逻辑"，或者对着一个根本不是 bug 的现象瞎改。

**这个 skill 做了什么**：

- 后端是一个 Chroma 向量库，产品使用文档已切片入库，支持中文语义检索
- SKILL.md 教 AI：碰到涉及产品功能/业务逻辑的 bug 时，**先跑查询脚本检索相关文档，搞清楚功能预期，再动手改代码**
- 内置了防幻觉规则：返回结果带 `relevance_distance`，距离都大于阈值就如实告知"文档里没有相关信息"，不强答、不凭代码反推业务

**典型使用场景**：

- 用户报"导出按钮点了没反应"——先查文档确认导出功能的触发条件、权限要求、数据范围
- 某个字段展示不对——先查文档确认字段的业务含义、计算规则、展示格式
- 状态流转异常——先查文档确认各状态之间的合法路径

**分享点**：这是**给开发侧用的轻量 RAG**，不是面向用户的产品客服。价值在于让 AI 在改代码之前先建立"产品预期"的上下文，减少"代码层面修对了、产品层面改错了"的情况。防幻觉规则（阈值判断 + 允许说"文档里没有"）同样关键——文档查不到时，应该提示开发者去找产品或需求方确认，而不是让 AI 自己编一套业务逻辑。

### 3.2 dev-team-dialogue — 一个人也能开"技术评审会"

**解决的痛点**：做技术决策时问 AI，得到的往往是一个四平八稳、什么都对但没有立场的答案。而真实团队评审的价值恰恰在于**不同立场的碰撞**。

**这个 skill 做了什么**：

- 定义了五个风格原型工程师，各有固定的哲学和说话风格：
  - 🔴🏗️ arch：架构与边界，严苛直接
  - 🟣📐 algo：正确性与复杂度，爱用反例戳假设
  - 🟠♻️ refactor：整洁与演进，温和但执着
  - 🟢✅ xp：TDD 与小步快跑
  - 🔵🚀 pragma：先跑起来再说，反过度设计
- 按话题类型自动选主导角色 + 1~2 个插话角色，不是五个人轮流念稿
- **允许角色吵架不和解**：比如"要不要上微服务"，arch 和 pragma 可以直接对呛，把判断留给用户

**分享点**：这是"人格化 skill"的玩法——价值不在于答案本身，而在于**强制 AI 从多个互斥的立场各自论证**，把决策的 tradeoff 摊开给你看。适合方案评审前自己先过一遍。

## 四、写好一个 Skill 的经验总结（5 分钟）

从这 6 个 skill 里能提炼出几条通用经验：

| 经验 | 例子 |
|------|------|
| description 是路由，要写触发场景和口语化触发词 | quick-commit 把"快捷提交""跳过检查""强行提交"都写进 description |
| 输出协议模板化，结果才稳定可用 | diff-git-review 的三级分层模板、iconfont 的固定输出格式 |
| 流程约束比能力增强更常用 | legacy-feature-kickoff 全篇都在管"先做什么后做什么" |
| 确定性的事交给脚本，模糊判断留给 AI | iconfont 的搜索/渲染脚本、product-docs-query 的向量检索脚本 |
| 给 AI 留"说不知道"的出口，防幻觉 | product-docs-query 查不到文档时提示找产品确认，不凭代码反推业务 |
| 高度场景化的 skill 用手动触发 | iconfont 的 `disable-model-invocation: true` |
| skill 之间可以设计衔接与制衡 | review 通过才给提交命令，Blocking 时禁止快捷提交 |

## 五、Demo 建议（现场演示脚本）

1. **主线串演**（推荐重点）：拿一个真实小需求 →
   - 丢 PRD + Figma 链接，看 kickoff 输出计划清单（不写代码）
   - 实现中贴一张 icon 截图 `@iconfont`，看它搜索 + 渲染比对
   - `git add` 后说"提交前帮我看看"，看分层 review 结果
   - 修完问题后说"快捷提交"，拿到一条免检命令
2. **product-docs-query**：拿一个真实 bug 描述（如"XX 页面导出失败"），看 AI 是否先检索产品文档理解功能预期，再给出修复方向；再换一个文档里没有的功能，看它会不会说"查不到，需要确认预期行为"
3. **dev-team-dialogue**：现场抛一个团队里真实争论过的技术选型，看 arch 和 pragma 吵架
